# SQLite 大规模导入与并发读取验收

本轮验证首次管理员初始化保护，以及 SQLite 在持续读取期间的后台批量导入。应用源码对应 `5f4dd9c`；本地镜像 ID 为 `sha256:8a63e2f61b77d883bc4033ecdb19d67fb078088f5bf88e1ae0b253a5510149df`。镜像在提交前构建，内置构建标记为 `9f73a47-perf-fixes`，不代表已发布版本。

## 环境与方法

宿主为 Linux 6.12.107、Intel i5-12400，4 个可用逻辑 CPU。应用以 Go 1.27.1、`CGO_ENABLED=0` 构建，在 scratch 容器中以 UID/GID 65532 运行，根文件系统只读。应用固定 CPU 0、限额 1 CPU、内存和 memory+swap 上限均为 1 GiB；`GOMEMLIMIT=768MiB`，未显式设置 `GOMAXPROCS`。k6 0.54.0 固定 CPU 2–3，编排和辅助工作固定 CPU 1。使用独立命名卷和仅回环可访问的随机端口，无 Nginx 或公网链路。

SQLite 临时目录为 256 MiB 私有 tmpfs，上传上限 128 MiB，导入期限 180 秒，快照加载期限 120 秒，版本轮询间隔 5 秒。保持默认日志级别，配置每份 10 MiB、保留两份的 Docker 日志轮转。宿主仍运行其他服务，因此结果是本机实测，不是跨硬件保证。

夹具由 `scripts/generate-fixture.go` 以固定随机种子 `20260918` 生成，包含中文、emoji、不均匀分类和超过 1000 码点的语句。先导入 12000 条，再于持续负载启动后的约 130、205、280 秒分别通过真实管理员 HTTP 页面导入 100000 条，UUID 范围互不重叠。初始文件 2646780 字节，各批文件均为 22114419 字节。最终应有 312001 条语句，包含首次启动的 1 条示例。

预热 60 秒、100 RPS；正式测量 600 秒、1000 RPS，三种请求均匀混合：默认随机、多分类、长度过滤。使用固定到达率，不以延迟变化降低发送率。额外将正式测量第 60–300 秒标记为导入窗口，该窗口覆盖三批完整的上传、预览、提交和刷新，也包含批次间的正常读取，不能解释为仅事务执行瞬间的延迟。

严格门槛为：正式阶段至少完成 600000 个请求、无丢发、全部有效请求返回 200、HTTP 失败率为 0，整体及导入窗口 P95 均小于 10 ms。每批确认后验证最后一条 UUID 可从 API 查询，结束后停机检查 SQLite 完整性、外键、语句总数及管理员数。内存每秒采样，额外读取 cgroup 原生峰值和 OOM 计数。

## 压测前发现并修复的问题

1. scratch 容器没有可写临时目录时，12000 条批量写入失败。已在镜像预建 `/tmp`，Compose 提供可配置的私有 tmpfs。
2. 64 MiB tmpfs 在 312001 条规模下可复现「已提交、快照刷新失败」，同一修复镜像使用 256 MiB 时完整预检通过。Compose 默认值改为 256 MiB，通过 `SQLITE_TMPFS_SIZE` 调整；这属于资源容量配置，不是句库条目数限制。
3. UUID 查重原先对字段应用 `LOWER/REPLACE`，每 500 条输入重复扫描已有句库。改为使用现有 UUID 索引，并额外扫描一次非规范 UUID，保留相关损坏记录的冲突检查；不增加 schema 版本。
4. `web admin create` 改为只允许首次初始化。SQLite 和 MariaDB 的并发初始化、密码重置与旧凭据登录竞争测试通过，真实容器 CLI 也验证重复初始化被拒绝。

修复前的持续负载尝试未跑完：首两批 100000 条总耗时约 6.73 秒和 35.23 秒，第三批提交后刷新失败。此尝试不能当作完整性能验收。[预检与失败证据](validation/sqlite-20260929/preflight.json)保留了结果。

## 64 VU 正式测量：未通过

预分配 64 VU、最多 256 VU；实际发生动态扩容。正式阶段完成 599996 个请求，按 600 秒计算为 999.993 RPS，丢发 5 次；HTTP 失败为 0，全部已发起请求的检查通过。整体 P95 为 0.213 ms，导入窗口 P95 为 7.811 ms，稳定窗口 P95 为 0.190 ms，最大响应耗时为 91.945 ms。请求数和零丢发门槛未满足，因此结果为未通过。

三批 100000 条的上传/预览分别为 0.754、0.878、0.857 秒，写入/刷新分别为 2.818、3.707、4.986 秒。最终数据完整性通过，语句数为 312001，管理员数为 1。661 次采样的最大 RSS 为 821575680 字节；cgroup memory.peak 为 1073750016 字节，memory.max 事件 139 次，OOM 和 OOM kill 均为 0。峰值贴近 1 GiB 上限，此配置没有充足内存余量。

丢发与负载工具扩容同时出现，但这些证据不足以单独归因于客户端或应用。下一轮只提高预分配 VU 至 128，保持应用资源、请求速率、持续时间和门槛不变。

原始数据：[运行报告](validation/sqlite-20260929/64-vus/report.json)、[k6 汇总](validation/sqlite-20260929/64-vus/summary.json)、[内存采样](validation/sqlite-20260929/64-vus/memory.csv)。k6 导出中子指标的 `rate` 使用包含预热的总时长，报告的正式 RPS 按正式请求数除以 600 秒计算。

## 128 VU 复测：通过

仅将每个场景的预分配 VU 从 64 提高至 128，其余应用配置、负载、数据和阈值保持不变。预热后测量完整 600 秒，完成 600001 个请求，即 1000.002 RPS；丢发为 0、HTTP 失败为 0、有效请求检查全部通过，k6 退出码为 0。此次配置下通过既定验收门槛，不等同于证明之前的丢发只由客户端引起。

## 实现级分配基准

在管理 CPU 上执行现有 `BenchmarkRandomRequest`：100 条与 10000 条均为 9835 B/op、75 allocs/op，耗时分别为 8634 ns/op、10448 ns/op。该小规模实现基准未观察到分配量随句库规模线性增长，不能替代 HTTP 压测，也不等同于已验证 312001 条的单请求分配量。

## 复现与范围

先构建本地镜像，然后运行：

```bash
PYTHONDONTWRITEBYTECODE=1 python3 scripts/verify-sqlite-performance.py \
  --image quotewisp:perf-validation \
  --k6-image grafana/k6@sha256:1f40432b1cbe7234e977f96c362c9bc550a2d2b583d014dd8669fe40d3e9e755 \
  --vus 128 --output repo.cache/sqlite-performance-new-run
```

输出目录必须是新目录。可加 `--preflight-only` 先验证全部批次；`--tmpfs-mib 64` 可复现本轮小临时目录的容量边界。工具会清理自己的容器和数据卷，保留合成测试的报告、k6 日志和内存采样，不接收生产目标地址。

本次大批量性能测量使用原生 JSON；Hitokoto 的功能及恢复验证见 [镜像与恢复记录](sqlite-release-validation.md)。没有在本轮执行数据库故障注入、慢客户端专项、大文件 Hitokoto 性能、MySQL 8.4 验收或生产部署。
